# V2 current Content Rewards contracts

Observed current first-party public client and authenticated native JSON API on 2026-10-09. Identity GET `/api/user/users/me` binds GET `/api/user/social-media-accounts?userId=...` to the logged-in user. The exact TikTok account is active with bio verification; OAuth is not required by this observed CR account contract. Campaign GET `/api/campaign/campaigns/:id` returns own `id`, `joined`, `requiresApplication`, `access.canSubmit` and explicit configuration requirements. The sampled public campaign has joined=false, requiresApplication=false, canSubmit=true: submission access alone is not enrollment.

GET `/api/campaign/campaigns/applications/me` returns `{applications:[],partialFailure:false}` for the authenticated account. Public application UI distinguishes pending/approved/rejected/withdrawn and selected socialAccountIds. Native probe accepts approval only for the exact campaign and exact posting account on a complete listing. No application acceptance or brand draft approval has been observed live. Enrollment never creates a brand-approval grant.

GET `/api/submission/submissions` returned 17 records with own campaignId, id, isDeleted and nested socialMediaPost.postUrl. Pagination has count=17, limit=20, nextCursor=null. Lookup now uses this API, requires literal same-row campaign/URL equality and ignores deleted rows. Absence requires parseable records, matching count and terminal cursor. Nonterminal cursors are followed with bounded same-origin GETs (five pages, at most 100 items/page, one 16-second deadline); partial, repeated or exhausted pagination remains UNKNOWN. No reward submission was sent in this phase.

Join is a distinct bodyless POST `/api/campaign/campaigns/:id/join`; application is POST `/api/campaign/campaigns/:id/apply` with applicationId, form response and selected socialAccountIds. Generic forms requiring personal answers are unsupported; no fabricated answers or application acceptance. The narrow join action rechecks public/non-application campaign scope, exact active posting account, canSubmit and joined before POST. Only fresh exact joined=true readback can confirm. V2 owns the durable mc.reward_join_attempt write-ahead: at most one network attempt per campaign/platform/account, ambiguous/crashed attempts reconcile by reads without resend. Actual joining remains unproven while mutations are killed.

`MOMENTCIRCUIT_V2_CR_MUTATIONS_ENABLED` defaults false and kills joining and reward submission server-side. Current production must remain false/unset during this phase. V2 also requires shadow=false and reward kill=false plus current executable rights/eligibility and an unchanged fresh capture before automatic joining. No cookies leave Halyard. Same-origin session refresh/rotation and the private vault are preserved.

HTTP200 never establishes readiness. Verification: 52 focused bridge tests, web typecheck and affected lint; independent authenticated preview/read-only worker observations.
